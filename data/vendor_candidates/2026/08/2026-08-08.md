## 🔧 Known defects observed this run

These are properties of the sweep scripts, not of today's data. Reported, not fixed.

### 1. `blog_url_hint` gate rejects almost everything — 115 orgs this run

Step C.5 requires a non-empty `blog_url_hint` before a candidate can be written into `enterprise_vendors`. **Nothing in the pipeline ever populates that field** — it only exists for orgs seeded by hand or by `seed_orgs.json`. This run:

- **115 candidates rejected for this reason alone** — 114 at promote tier, 1 at hot-event tier (`taalas`).
- **43** of those are unambiguous named entities with no alias hazard (`siemens` 42 mentions, `alibaba` 41, `huawei` 27, `adobe`, `roche`, `bcg`, `gartner`, `bytedance`, `stanford-hai`, `future-of-life-institute`, `exeon-analytics`, `artificial-analysis`, `ibm-research`, …).
- **77 of the 114 promote-tier rejects have held promote for ≥10 consecutive runs.**
- **`oracle` is at 14 consecutive days at promote** — and 14 is the cap on `classification_history`, so the true streak is *at least* 14 and unknowable from the record.
- Total applied promotions this run: **0**. Total applicable candidates: **0**.

Net effect: the auto-promote path is essentially inert for any org the pipeline discovered itself. Fixing it means populating `blog_url_hint` at discovery time (the collectors already hold the first-party permalinks) or letting Step C write a `fallback_search`-only entry.

### 2. The silent-vendor check reads mention counts, not feed health — 40 configured vendors produced zero mentions today

`covered_silent` is decided by `last_seen`, which any text match anywhere in the corpus refreshes — including the news collector's own coverage telemetry. So a vendor whose configured feed is dark reads `covered_healthy` as long as somebody else writes about it.

- **`covered_silent` count today: 0.** **Configured vendors (priority + enterprise) with zero mentions in any of today's six source files: 40** of 74.
- Longest-quiet of those: `manus` (25d since last mention), `helsing` (18d since last mention), `norm-ai` (14d since last mention), `netflix` (9d since last mention), `amazon-aws` (5d since last mention), `broadcom` (5d since last mention).
- **2 vendors whose *only* hit today is the collector's own telemetry line** — `n8n` and `workday_oracle`. Both are on their fourth consecutive dead-feed day; both read `covered_healthy`.
- **12 more vendors are telemetry-inflated** (part of today's count comes from the coverage block, not editorial text): `amd` 17→16, `anthropic` 18→17, `deepseek` 9→8, `meta` 17→16, `mistral` 17→16, `nvidia` 62→60, `openai` 62→61, `redhat_ibm` 19→17, `salesforce` 14→13, `sap` 19→17, `servicenow` 12→11, `snowflake` 10→7.

### 3. The velocity→hot_event path is unreachable dead code

```
velocity_28d_avg = mentions_28d / 4          # and mentions_28d >= mentions_7d, always
velocity_ratio   = v7 / max(v28_avg, 1.0)
                 = v7 / max(v7/4, 1.0)  <=  4.0   whenever v7 >= 4
hot_event_velocity_threshold = 5.0
```

The ratio is bounded above by **4.0** and the trigger is **5.0**, so `velocity_status: "surging"` can never be assigned and the second (keyword-free) hot-event path in §4 never fires. Confirmed against today's numbers: **max `velocity_ratio` across all 1766 orgs = 4.0**, **surging = 0**, and **62 orgs sit exactly at the 4.00 ceiling** — a saturated statistic, not a distribution. Every hot event this pipeline has ever applied came in through the keyword path.

Either threshold must drop below 4.0, or the baseline must exclude the recent window (`(28d − 7d)/3`), which would let the ratio exceed 4.
