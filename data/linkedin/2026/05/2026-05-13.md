- **ISO/IEC 42001 and the EU AI Act: Certification is not the same as compliance** — Matej Jambrich, Dentons Europe CTO (en, ~7.5k chars, May 10). Board-facing primer that dismantles the increasingly common "we're ISO 42001 certified, so we're AI-Act-compliant" misconception. Three reasons it fails: 42001 is a management-system standard (governs the organisation), the AI Act regulates specific actors and specific systems, and a presumption of conformity under the Act only triggers when harmonised standards are cited in the Official Journal — ISO certificates don't trigger that presumption. Documents the live Digital Omnibus trilogue timeline in unusual detail: 19-Nov-2025 Commission proposal to defer high-risk deadlines to 2-Dec-2027 (Annex III) and 2-Aug-2028 (Annex I); Council general approach 13-Mar-2026; Parliament negotiating mandate 26-Mar-2026 by 569-45; second political trilogue ran ~12h on 28-Apr-2026 and ended without agreement at dawn 29-Apr — the dispute was over conformity-assessment architecture for Annex I, not the postponement itself; next trilogue ~13 May 2026 (today). The hard wall remains 2-Aug-2026 if the Omnibus is not adopted by then. Then proposes a five-component overlay model (classification gateway, system-level evidence file, supplier control model, change-control trigger, board/management reporting) and the four things a mature org should produce on demand (live AI inventory, classification + risk assessment per system, working control evidence, management-review process driving corrective action). _Why interesting:_ The most disciplined operational answer to "what governance posture should we hold on 13 May" — written by someone who tracks the trilogue calendar to the hour and holds the 42001 Lead Implementer credential. Directly relevant given today is the next trilogue date. [https://www.linkedin.com/pulse/isoiec-42001-eu-ai-act-certification-same-compliance-matej-jambrich-fdjnc]

- **The Agent Internet Has a Cryptography Problem — and It's Worse Than the Scores Suggest** — Dr. Mark Tehrani, CyberSeQ (en, ~8k chars, May 6). Post-quantum cryptography audit of the five leading agent protocols (MCP, A2A, ACP, ANP, AITP) using the CyberSeQ Discovery Engine static scanner against NIST SP 800-131A Rev. 2, NSA CNSA 2.0, and FIPS 140-3. Documents two failure modes: (1) cryptography not defined — ANP scores 100% quantum-ready on a surface of only 3 detected crypto instances; A2A scores 84% but 77 of 92 instances are "TLS (unspecified version)" — the high scores are "denominator artefacts, absence of cryptography mistaken for resistance"; (2) cryptography defined but weak — MCP is 82 of 83 instances RSA-2048 (NIST allows until 2030, CNSA 2.0 already disallows, "harvest now, decrypt later" applies), ACP ships 45 deprecated-SSL + 27 RSA-2048, AITP ships 21 deprecated-SSL + 15 RSA-2048. Zero of the five meet CNSA 2.0 mandatory PQC; zero are fully FIPS 140-3 compliant; zero ship ML-DSA / ML-KEM / any NIST-standardised PQC algorithm. Calls on Linux Foundation governance bodies (MCP, A2A, AGNTCY) to mandate (not suggest) specific primitives, require ML-DSA-65 + ML-KEM-768 tiers, ship hybrid classical+PQC modes by default, and rotate every agent identity before 2030. _Why interesting:_ Rare quantitative governance piece — directly relevant to the user's MCP/A2A interoperability focus area, and a strong counterweight to the "protocols are ready" framing. The "harvest now, decrypt later" frame on signed agent messages is the operationally hardest argument. [https://www.linkedin.com/pulse/agent-internet-has-cryptography-problem-its-worse-than-tehrani-xivre]

- **MCP Server Security Best Practices to Prevent Risk** — Rohit Ganguly, Descope (ex-Microsoft) (en, ~12k chars, originally Feb 25 2026, republished as Pulse May 8). Eight-section production checklist for MCP deployments, with primary-source datapoints: Knostic scanned ~2,000 public MCP servers and found every verified instance granted internal tool listings without authentication; Backslash Security found another pool bound to 0.0.0.0 with arbitrary-code-execution exposure; recent analysis of 5,000+ open-source MCP servers found over half stored downstream credentials as static API keys or PATs in environment variables, with only a small fraction using OAuth. The eight practices: (1) separate authorization server from resource server — June 2025 spec revision formalised MCP servers as OAuth Resource Servers; (2) OAuth 2.1 + PKCE done properly, with RFC 8707 Resource Indicators to bind tokens to servers; (3) user auth and SSO before any agent action; (4) consent management with time-bound, scoped consent; (5) tool-level scope-based access control with progressive scoping; (6) support all three client registration methods (CIMD now the SHOULD default per spec revision, DCR optional, pre-registration for curated setups); (7) credential vaults instead of env-vars for downstream secrets; (8) full audit logging across registration → consent → connectivity → termination. Vendor piece (closes with Descope pitch) but the substance is OWASP GenAI Security Project-aligned and primary-source-dense. _Why interesting:_ The most actionable MCP-security checklist this week; pairs well with Tehrani's cryptography piece for an end-to-end identity-and-protocol governance read. [https://www.linkedin.com/pulse/mcp-server-security-best-practices-prevent-risk-rohit-ganguly-6ta0e]

Documents four recurring risk patterns (overprivilege without visibility, no real-time enforcement, impersonation via human identity, zero accountability) and grounds them in primary research: Microsoft's 2025 Work Trend Index says 81% of leaders expect agents in their AI strategy within 12-18 months; HashiCorp's 2025 Cloud Complexity Report says 97% of orgs use multiple cloud tools and 73% report platform/security misalignment; Gartner estimates machine identities outnumber human identities >45:1; IBM's 2025 Cost of a Data Breach Report says of orgs reporting AI-related incidents, 97% lacked AI-specific access controls and 63% had no AI governance.
